# Architecture overview

Trip Side Kick is a modular monolith: one web host serves a Razor brochure at
`tripsidekick.net` and a React PWA and `/v1` API at `tripsidekick.app`. The
target runtime uses a private PostgreSQL database and persistent local keyring
and document mounts. See the [runtime contract](workload-consolidation.md) for
deployment boundaries and configuration.

## Host isolation

`HostSurfaceMiddleware` rejects unconfigured hosts and redirects configured
`www` hosts to their apex. Endpoint `RequireHost` conventions and host-scoped
static-file middleware independently restrict brochure pages and `SiteAssets/`
to the site surface and controllers, OpenAPI and the generated `wwwroot/` PWA
to the app surface. `wwwroot/` is generated by the client build and is not
source-controlled.

Health and information endpoints are available on configured hosts, not
arbitrary hosts. The health routes are `/api/health/live` and
`/api/health/ready`; readiness checks the database connection and pending
migrations. Forwarded host is not trusted. Forwarded HTTPS and client IP
headers are accepted only from configured proxies and framework loopback
defaults.

## Project boundaries

Dependencies point inward: Domain defines aggregates and invariants;
Application defines services and repository interfaces; Infrastructure provides
EF Core repositories; Web composes the host, middleware and HTTP endpoints.
The test project covers the layers and their integration.

Dates use Noda Time, money uses decimal amounts and ISO currency codes, and
identifiers use UUIDv7. PostgreSQL generates opaque byte-array concurrency
values used by HTTP ETags. See [data and persistence](data-and-persistence.md)
and [identity and access](identity-and-access.md).

Server and browser telemetry are configured by the application; preserve
`AddObservability()` and never emit trip or document content, booking
references, email addresses or display names in telemetry.
